이번 시간은 16대가 모두 살아난 다음부터의 일상을 다룹니다. 시스템을 ‘만드는 일’은 한 번이지만, ‘운영하는 일’은 1년 내내, 어쩌면 졸업 뒤 후배에게 인계하는 그 다음 해까지 이어집니다. 시스템이 가장 위험한 순간은 만들고 있을 때가 아니라 ‘잘 굴러간다고 믿기 시작했을 때’입니다.

이번 단원의 학습 흐름은 ‘작은 점검을 자주, 큰 점검을 가끔’입니다. 매일 5분이 걸리는 일일 점검, 일주일에 한 번의 주간 점검, 한 달에 한 번의 월간 점검 — 이 세 층으로 운영팀의 일과가 짜입니다. 한편 무엇인가 망가졌을 때를 위한 ‘장애 대응 매뉴얼’도 미리 만들어 둡니다. 사고가 난 뒤에 매뉴얼을 쓰면 늦습니다.

여기서 한 가지 짚어 둘 점이 있습니다. 학생 운영팀이 정말로 잘 일하게 만들려면, ‘무엇을, 왜, 어떻게’가 모두 명확해야 합니다. ‘대시보드를 매일 보세요’만 부탁하면 한 달 뒤 운영팀이 사라집니다. ‘이 다섯 줄을 매일 봐 주세요. 이 다섯 줄이 알려 주는 것은 학교 환경의 건강이고, 이 다섯 줄에 빨간색이 보이면 우리가 행동해야 합니다’라고 설명할 때 운영팀이 머뭅니다. 이번 단원이 그 ‘다섯 줄 운영’의 모양을 정해 봅니다.

## 이번 시간의 미션

운영팀이 1년 동안 다음 세 가지를 모두 자연스럽게 수행할 수 있게 됩니다.

1. 매일 5분 ‘다섯 줄 점검’을 빠르게 끝낸다.
2. 노드 하나가 죽었을 때, 30분 안에 원인을 찾아 복구하거나 예비 노드로 교체한다.
3. 한 달에 한 번 분석팀과 함께 ‘환경 리포트’를 발표한다.

> **🧠 컴퓨팅 사고력 · 운영의 세 시간 단위**
>
> 1. **분 단위(실시간)**: 대시보드의 🚨 표시. 노드 하나가 죽었을 때.
> 2. **일 단위**: 등교 직후 5분 점검. 어제 밤사이 무슨 일이 있었는가.
> 3. **주·월 단위**: 데이터 품질, 환기 패턴, 장애 통계.
>
> 세 시간 단위가 서로를 보완합니다. 분 단위만 보면 큰 그림을 놓치고, 월 단위만 보면 사고를 놓칩니다.

> 📷 **그림 4-1** · 대시보드 ‘전체 교실’ 탭의 16개 카드 격자
> *촬영 메모 — Streamlit 대시보드의 ‘전체 교실’ 탭. 4×4 격자에 16개 노드 카드가 모두 적정(🟩) 색상으로 보이는 평상 상태.*

## 단계 1 — 일일 점검 (운영팀 학생, 5분)

등교 직후 운영팀 학생이 자기 자리에서 스마트폰이나 노트북으로 대시보드를 한 번 엽니다.

### 1.1 다섯 줄 점검

1. 16개 카드가 모두 보이는가?
2. 🚨 표시된 카드가 있는가?
3. 모든 카드의 ‘마지막 수신’이 5분 이내인가?
4. 명백히 이상한 값이 있는가? (예: T=-45°C, lux=0 고정)
5. 어제 밤사이 새로 ‘빨간색(위험)’이 켜졌던 시간대가 있는가?

이 다섯 줄을 매일 같은 순서로 봅니다. 어떤 한 줄이 ‘아니오’이면 그 줄에 해당하는 대응 절차로 갑니다.

> **Tip 다섯 줄을 그대로 적어 두기**
>
> 1. 운영팀의 공용 공간(슬랙·노션·구글 시트 어디라도)에 다섯 줄을 ‘점검 양식’으로 박아 둡니다.
> 2. 매일 다섯 줄에 ‘OK/NG’를 체크하는 방식이면 점검 시간이 1~2분으로 줄어듭니다.
> 3. NG가 났을 때만 사진을 남기고, OK일 때는 체크만 하는 방식이 가장 가볍게 굴러갑니다.

### 1.2 점검 한 줄 일지

매일 한 줄, 다음 형식으로 점검 결과를 남깁니다.

```
2026-05-21 오전 8:35  운영팀: 김ㅇㅇ  결과: OK / 1-3 일시 미수신(15분간), 자동 복구
```

이 한 줄이 한 달 모이면 ‘우리 학교의 한 달 안정성’이 됩니다.

> 📷 **그림 4-2** · 🚨 표시된 노드 카드 클로즈업
> *촬영 메모 — 16개 카드 중 한 장에 🚨 표시와 ‘마지막 수신: 30분 전’이 보이는 화면. 다른 카드는 모두 적정 색상이라 한 장만 두드러져 보이게.*

## 단계 2 — 노드 1대 죽음: 30분 복구 절차

대시보드에 🚨가 떴습니다. 30분 안에 정상으로 돌리는 표준 절차입니다.

### 2.1 5분: 원격 점검

| 점검 | 도구 |
|---|---|
| 같은 NODE_ID의 측정이 정말 끊겼는가 | 대시보드 ‘교실 상세’ 탭의 시계열 |
| 다른 노드는 정상인가 (전체 망 장애 아닌지) | ‘전체 교실’ 탭 한눈에 확인 |
| 서버 자체는 살아 있는가 | `curl http://192.168.0.10:8000/health` |

서버가 죽었거나 다수 노드가 동시에 끊겼다면 단계 3으로 갑니다.

### 2.2 10분: 현장 점검

해당 교실로 갑니다(운영팀 페어 2명, 가능하면 교사 동행 또는 사후 보고).

| 점검 | 결과 | 대응 |
|---|---|---|
| Pico 본체 LED | 꺼짐 | 전원 단계 의심 → USB 케이블·어댑터·콘센트 재확인 |
| LED 켜짐, 셸 출력 없음 | 펌웨어 의심 | USB 재꽂기 → 자동 와치독 재부팅 기다림 |
| 측정값이 0 또는 -45 같은 극단값 | 케이블 빠짐 의심 | 박스 열어 Grove·점퍼 재연결 |

### 2.3 15분: 복구 또는 교체

| 상황 | 대응 |
|---|---|
| 케이블 재연결로 정상 복구 | 매핑표 ‘점검·복구 이력’ 한 줄 추가 |
| 센서 자체 의심 | 예비 모듈로 교체(2분 작업) |
| 펌웨어 의심 | Unit 3 배포 스크립트로 재배포 |
| 정말 모르겠음 | **예비 노드 통째 교체** → 죽은 노드는 조립팀 작업장으로 회수 |

> **🤖 AI에게 물어보기 · ‘이 노드만 죽는 이유’**
>
> 1. 같은 노드가 자꾸 죽는다면 챗 LLM에 ‘기후행동365 16노드 중 한 대만 자주 끊깁니다. 가장 흔한 원인 다섯 가지를 알려 주세요’라고 부탁해 봅니다.
> 2. ‘교실 안 무선 신호가 약한 자리’ ‘USB 어댑터의 노이즈’ ‘박스 결로’ 같은 답이 나옵니다.
> 3. 가설을 하나씩 검증해 가며, 우리 학교의 진짜 원인을 찾습니다.

> 📷 **그림 4-3** · 예비 노드로 교체하는 운영팀 학생
> *촬영 메모 — 학생이 죽은 노드의 USB를 빼고 예비 박스를 콘센트에 꽂는 순간. 라벨이 ‘1-3 1학년 3반’으로 보이게.*

## 단계 3 — 다수 노드 동시 죽음: 망 장애 의심

3개 이상의 노드가 동시에 🚨 — 이때는 한 노드를 만지러 가지 않습니다. 망 또는 서버 자체를 먼저 봅니다.

### 3.1 서버 상태

#### 코드 4-1

```bash
sudo systemctl status climate365
sudo systemctl status climate365-dashboard
sudo journalctl -u climate365 -n 50
```

`active (running)`이 아니면 다음을 시도합니다.

```bash
sudo systemctl restart climate365
```

### 3.2 망 상태

라즈베리 파이가 자기 게이트웨이로 핑이 통과되는지 확인합니다.

```bash
ping -c 3 192.168.0.1
```

응답이 없으면 학교 망 자체에 문제가 있습니다. 망 관리자(본인)가 학교 AP 또는 스위치를 점검합니다.

### 3.3 동시 다발 죽음의 4대 원인

| 원인 | 신호 |
|---|---|
| 서버 다운 | `systemctl status`가 failed |
| 학교 망 장애 | 다른 와이파이 기기도 끊김 |
| 정전 또는 PoE 차단 | 라즈베리 파이도 같이 꺼짐 |
| 일제 펌웨어 오류 | 직전에 단체 재배포가 있었음 |

펌웨어 오류가 가장 무섭습니다. **재배포는 한꺼번에 16대가 아니라 1~2대로 먼저 검증한 뒤** 나머지에 적용하는 ‘카나리(canary) 배포’를 권장합니다.

> **🔬 가설을 세워 봅시다 · 카나리는 정말 필요한가**
>
> 1. ‘16대를 한 번에 갈아 끼우면 빠르지 않을까’라는 유혹이 있습니다.
> 2. 하지만 한 번 잘못된 코드가 16대에 동시에 들어가면, 16개의 교실이 동시에 깜깜해집니다.
> 3. ‘1대 → 확인 → 16대’라는 카나리 패턴 한 줄이 사고를 막습니다.

## 단계 4 — 주간 점검 (운영팀 + 분석팀, 20분)

매주 한 번, 운영팀과 분석팀이 모여 ‘데이터의 품질’을 함께 봅니다.

### 4.1 데이터 품질 4가지

1. **결측률**: 노드별로 한 주간 받은 측정 건수가 기대치(28,800건/노드)에 가까운가?
2. **이상치**: 명백히 비현실적인 값이 며칠 동안 쌓이지 않았는가?
3. **고정값**: 같은 값이 30분 이상 한 글자도 안 변한 노드가 있는가? (센서 고장 신호)
4. **분포 이동**: 지난주와 비교해 어느 노드의 평균이 갑자기 변했는가? (위치 변경 또는 환경 변화)

### 4.2 SQL 한 줄로 보는 결측률

라즈베리 파이에 SSH 접속해 다음을 실행합니다.

#### 코드 4-2

```sql
sqlite3 /home/pi/climate-action-365/prototype/server/data.db <<EOF
.mode column
.headers on
SELECT node_id,
       COUNT(*) AS got,
       28800 AS expected,
       ROUND(COUNT(*)*100.0/28800, 1) AS rate_pct
FROM readings
WHERE received_at >= datetime('now','-7 days')
GROUP BY node_id
ORDER BY rate_pct;
EOF
```

##### 실행 결과

```
node_id  got     expected  rate_pct
3-2      24530   28800     85.2
1-7      26010   28800     90.3
1-1      28122   28800     97.6
...
```

`rate_pct`가 가장 낮은 노드부터 봅니다. 90% 미만 노드는 ‘점검 대상’으로 매핑표에 표시합니다.

> 📷 **그림 4-4** · 분석팀 작업장 탭에서 4개 교실을 비교하는 화면
> *촬영 메모 — Streamlit ‘🧪 분석팀 작업장’ 탭. 4개 교실의 온도 시계열이 한 그래프에 겹쳐 있고, 아래에 ‘기준 위반 횟수’ 표가 보이게.*

> **📊 데이터 잠깐 들여다보기 · 결측은 우연이 아니다**
>
> 1. ‘이 노드만 90%’ 같은 상황은 우연이 아닐 가능성이 높습니다.
> 2. WiFi 신호 약한 자리, 콘센트 빠짐, 박스 결로 — 모두 데이터에 흔적이 남습니다.
> 3. 결측의 ‘패턴’이 보이면, 그 자리의 환경 문제를 발견한 셈입니다.

## 단계 5 — 월간 리포트 (분석팀 주관, 1시간)

한 달에 한 번, 분석팀이 ‘우리 학교의 한 달 환경 보고서’를 정리합니다. 운영팀과 교사도 함께 봅니다.

### 5.1 리포트 표준 골격

1. **이번 달 한 줄 요약**: “3학년 교실의 오후 조도가 학교보건법 기준 미달인 날이 가장 많았습니다.”
2. **세 개의 그림**: 16교실 평균 시계열 / 기준 위반 횟수 막대 / 가장 인상적인 한 교실의 24시간 그래프
3. **세 개의 발견**: 패턴, 이상, 가설
4. **세 개의 제안**: 환기 시간 조정 / 조명 추가 / 다음 측정 항목(Phase 2)
5. **다음 달 미션**: 분석·운영팀이 함께 정함

### 5.2 분석팀 ‘작업장’ 탭 적극 활용

`prototype/dashboard/app.py`의 세 번째 탭(`🧪 분석팀 작업장`)이 이 리포트의 첫 출발점입니다.

- 다중 교실 비교 → 패턴 발견
- 기준 위반 횟수 → 우선순위 결정
- 시계열 그래프 캡처 → 리포트 본문

### 5.3 데이터 직접 다루기

분석팀이 익숙해지면 SQL이나 Pandas로 직접 데이터를 만지는 단계로 갑니다.

#### 코드 4-3

```python
# 본인 컴퓨터에서 (data.db를 백업본으로 가져온 뒤)
import pandas as pd, sqlite3
conn = sqlite3.connect("data-20260521.db")
df = pd.read_sql("SELECT * FROM readings WHERE received_at >= '2026-05-01'", conn)

# 교실별 일평균 온도
df["day"] = pd.to_datetime(df["received_at"]).dt.date
daily = df.groupby(["node_id","day"])["temperature"].mean().unstack(0)
daily.plot(title="일평균 온도 (5월)")
```

##### 실행 결과

각 노드별 일평균 온도가 한 그래프에 겹쳐 그려집니다. 학기 중 가장 따뜻한 교실, 가장 변동이 큰 교실이 한눈에 보입니다.

> **🤖 AI에게 물어보기 · 보고서 한 페이지 자동 생성**
>
> 1. 챗 LLM에 ‘다음 표(노드별 위반 횟수)와 그림 세 장을 바탕으로 한 페이지 보고서를 한국어로 써 주세요. 학생 운영팀이 발표할 수 있는 톤으로’라고 부탁합니다.
> 2. AI가 만든 초안에서 ‘사실 확인이 필요한 줄’을 골라 우리 데이터로 다시 검증합니다.
> 3. AI는 글의 형태를, 우리는 사실의 정확성을 책임진다 — 이 분업이 가장 좋은 결과를 만듭니다.

### 5.4 분석팀 레시피북 — 자주 쓰는 SQL과 Pandas

월간 리포트가 익숙해지면, 분석팀이 자기만의 질문을 데이터에 던지기 시작합니다. 다음 다섯 묶음은 그 첫 출발점입니다. 외울 필요는 없습니다. 한 번씩 돌려 보고 결과가 어떻게 나오는지를 손에 익히면 충분합니다.

#### 코드 4-4 — 교실별 시간대 평균 (점심 시간 전후 변화 찾기)

```sql
sqlite3 /home/pi/climate-action-365/prototype/server/data.db <<EOF
.mode column
.headers on
SELECT node_id,
       CAST(strftime('%H', received_at) AS INTEGER) AS hour,
       ROUND(AVG(temperature), 1) AS avg_temp,
       ROUND(AVG(humidity), 1)    AS avg_rh,
       ROUND(AVG(lux), 0)         AS avg_lux,
       COUNT(*)                   AS n
FROM readings
WHERE received_at >= datetime('now','-7 days')
GROUP BY node_id, hour
ORDER BY node_id, hour;
EOF
```

읽는 방법: 각 교실의 24시간을 한 줄씩 본 뒤, 점심 시간(12~13시) 전후로 온도·습도가 어떻게 변하는지 살핍니다. 잘 환기되는 교실은 점심 시간 후 1~2시간이 지나면 평소 값으로 돌아옵니다. 안 되는 교실은 오후 내내 높은 상태로 머무릅니다.

#### 코드 4-5 — Pandas로 ‘요일×시간’ 히트맵

```python
# 본인 컴퓨터에서 (data.db 백업본 기준)
import pandas as pd, sqlite3, matplotlib.pyplot as plt

conn = sqlite3.connect("data-20260521.db")
df = pd.read_sql(
    "SELECT received_at, node_id, temperature FROM readings "
    "WHERE node_id='1-1' AND received_at >= '2026-05-01'",

df["received_at"] = pd.to_datetime(df["received_at"])
df["weekday"] = df["received_at"].dt.day_name()
df["hour"]    = df["received_at"].dt.hour

pivot = df.pivot_table(
    index="weekday", columns="hour", values="temperature", aggfunc="mean"
)
# 요일 순서 정렬
order = ["Monday","Tuesday","Wednesday","Thursday","Friday","Saturday","Sunday"]
pivot = pivot.reindex(order)

fig, ax = plt.subplots(figsize=(12, 4))
```

#### 코드 4-6 — ‘고정값 노드 자동 탐지’ SQL (센서 고장 신호)

```sql
sqlite3 data.db <<EOF
.mode column
.headers on
-- 최근 1시간 동안 어떤 노드의 측정값이 한 글자도 안 변했는가
SELECT node_id,
       COUNT(DISTINCT temperature) AS uniq_t,
       COUNT(DISTINCT humidity)    AS uniq_rh,
       COUNT(DISTINCT lux)         AS uniq_lux,
       COUNT(*)                    AS n
FROM readings
WHERE received_at >= datetime('now','-1 hour')
GROUP BY node_id
HAVING uniq_t = 1 OR uniq_rh = 1 OR uniq_lux = 1
ORDER BY n DESC;
EOF
```

`uniq_t = 1`은 ‘1시간 동안 온도값이 정확히 한 가지만 나왔다’는 뜻 — 센서가 고정값을 반환 중일 가능성이 높습니다. 실제 환경에서는 1시간 사이 최소 ±0.2°C의 자연 변동이 있어야 정상입니다.

#### 코드 4-7 — 두 교실 동시 비교 (Pandas)

```python
import pandas as pd, sqlite3

conn = sqlite3.connect("data-20260521.db")
df = pd.read_sql(
    """SELECT received_at, node_id, temperature, humidity, lux
       FROM readings
       WHERE node_id IN ('1-1','1-2')
         AND received_at >= '2026-05-15'""",
    conn,
)
df["received_at"] = pd.to_datetime(df["received_at"])

# 한 시간 평균으로 리샘플
agg = (df.set_index("received_at")
         .groupby("node_id")
         .resample("1H")
         .mean(numeric_only=True)
         .reset_index())

# 두 교실의 같은 시각 차이
pivot = agg.pivot(index="received_at", columns="node_id", values="temperature")
pivot["diff"] = pivot["1-1"] - pivot["1-2"]
print(pivot["diff"].describe())
```

‘두 교실의 온도 차이’ 분포를 보면, 1-1이 평균 1.2°C 더 따뜻하다거나, 표준편차가 큰 시간대가 있다는 식의 사실이 숫자로 잡힙니다. 환기·조명·자리 배치 가설을 데이터로 검증하는 첫걸음입니다.

#### 코드 4-8 — 학교보건법 ‘위반 시간’ 합산

```sql
sqlite3 data.db <<EOF
.mode column
.headers on
-- 지난 30일 노드별 기준 위반 측정 건수 (30초 주기 = 건수 × 30초 = 위반 누적 시간)
SELECT node_id,
       SUM(CASE WHEN temperature > 28 THEN 1 ELSE 0 END) AS hot,
       SUM(CASE WHEN temperature < 18 THEN 1 ELSE 0 END) AS cold,
       SUM(CASE WHEN humidity > 80    THEN 1 ELSE 0 END) AS humid,
       SUM(CASE WHEN humidity < 30    THEN 1 ELSE 0 END) AS dry,
       SUM(CASE WHEN lux < 300        THEN 1 ELSE 0 END) AS dark
FROM readings
WHERE received_at >= datetime('now','-30 days')
GROUP BY node_id
ORDER BY hot + cold + humid + dry + dark DESC;
EOF
```

이 한 쿼리만으로 ‘이번 달 가장 환경이 나쁜 교실 TOP 5’가 즉시 정렬됩니다. 월간 리포트의 표지 숫자로 그대로 옮길 수 있습니다.

> **📊 데이터 잠깐 들여다보기 · 한 줄 SQL이 한 페이지 리포트가 된다**
>
> 1. 위 다섯 묶음 중 가장 자주 쓰게 되는 것은 코드 4-8(위반 시간 합산)입니다. 이 한 쿼리의 결과가 곧 매월 학교 운영위원회에 들고 가는 자료의 본문입니다.
> 2. 코드 4-5(요일×시간 히트맵)는 ‘월요일 1교시’ ‘금요일 점심 직후’ 같은 패턴의 ‘이름’을 만들어 줍니다. 이름이 붙은 패턴은 학생들이 토론하기 쉬워집니다.
> 3. 코드 4-6(고정값 탐지)은 사후 점검이 아니라 ‘예방 점검’이 됩니다. 운영팀의 일주일 작업을 5분으로 줄여 줍니다.
